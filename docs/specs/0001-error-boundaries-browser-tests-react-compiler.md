## 1. 背景と目的

技術構成を 2026 年 11 月時点の標準と比べた結果、土台（React 19 / Vite 8 / Zod 4 / TanStack Query 5）は推奨どおりでした。一方で、商用アプリとして次の 3 点が不足していました。

| #   | 課題                                                              | 影響                                                                             |
| --- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 1   | 描画中に想定外のエラーが起きると、画面全体が真っ白になる          | 利用者は何もできず、再読み込みするしかない                                       |
| 1'  | 各画面が「読み込み中」「エラー」の分岐を個別に手書きしている      | 書き漏れや表示のばらつきが起きやすい                                             |
| 2   | コンポーネントテストが、ブラウザを模した環境（jsdom）で動いている | 本物のブラウザと挙動が違う部分（レイアウト、フォーカス、イベント）を検証できない |
| 3   | 再描画の最適化を手で書く前提になっている                          | 規模が大きくなると、最適化の書き漏れによる性能低下が起きやすい                   |

この仕様では、次の 3 つを導入してこれらを解消します。

- **A-1**: ErrorBoundary と Suspense によるエラー・読み込み表示の整理
- **A-2**: Vitest 5 への更新と、Browser Mode（本物のブラウザ）でのコンポーネントテスト
- **A-3**: React Compiler の導入

## 2. 対象外

- 見た目の変更（Tailwind CSS / shadcn/ui の導入）。優先度 B として別途扱う
- ルーティングライブラリの変更（TanStack Router への移行）
- API（`apps/api`）の動作の変更。API のテストは Vitest 5 に更新するだけで、引き続き Workers ランタイムで実行する

## 3. A-1: エラー・読み込み表示の整理

### 3.1 エラーの受け止め方（2 段構え）

| 境界             | 置き場所                                    | 受け止めるもの                         | 表示                                                                                 |
| ---------------- | ------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------ |
| アプリ全体の境界 | `main.tsx`（アプリの一番外側）              | どこにも受け止められなかった描画エラー | 「問題が発生しました」と、ページの再読み込みボタン、トップへのリンク                 |
| 画面単位の境界   | `Layout` の中、各画面（`<Outlet />`）の外側 | 各画面の描画エラーと、データ取得の失敗 | エラーの内容と「再試行」ボタン。**ヘッダーとメニューは残り、ほかの画面へ移動できる** |

画面単位の境界の動作:

1. 「再試行」を押すと、失敗したデータ取得をやり直し、画面を描画し直す（TanStack Query の `QueryErrorResetBoundary` と連携する）
2. 別の画面へ移動すると、エラー表示は自動で解除される（URL のパスが変わったら境界をリセットする）
3. API が返したエラーメッセージ（例: 「レッスンが見つかりません」）はそのまま表示する。想定外のエラーは「予期しないエラーが発生しました」と表示し、内部の詳細は画面に出さない
4. 受け止めたエラーは `console.error` に記録する

### 3.2 読み込み中の表示

- 画面単位の境界の内側に `Suspense` を置き、データの読み込み中は共通の「読み込み中…」を表示する
- 各画面は「データがある」前提で書けるようになり、`isPending` / `error` の分岐を書かなくてよくなる

### 3.3 データ取得の使い分け

| 種類                                                       | 使うもの                                  | 対象                                                                                   |
| ---------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------- |
| 画面を表示するのに必須のデータ                             | `useSuspenseQuery` / `useSuspenseQueries` | レッスン一覧・レッスン詳細・進捗・ブックマーク一覧・レッスン一覧（ノートの絞り込み用） |
| 利用者の操作で条件が変わり、画面の一部だけ更新したいデータ | `useQuery`（従来どおり、その場で表示）    | ノート一覧（検索・ページ送り）、パッケージ検索の結果                                   |
| ログイン状態                                               | `useQuery`（従来どおり）                  | `RequireAuth` が未ログインを判定してログイン画面へ送るため                             |

- 1 つの画面で複数のデータが必要なときは `useSuspenseQueries` で**並列に**取得する（`useSuspenseQuery` を続けて書くと、1 つ目の取得が終わるまで 2 つ目が始まらない「直列の待ち」になるため）
- ノート一覧とパッケージ検索を `useQuery` のままにするのは、検索のたびに画面全体が「読み込み中」に置き換わるのを避け、前の結果を表示したまま更新するため
- 送信操作（`useMutation`）のエラーは従来どおり、フォームの中に表示する

### 3.4 受け入れ条件

- [x] 画面の描画中に例外が起きても、ヘッダーとメニューが残り、エラー表示と「再試行」ボタンが出る
- [x] 「再試行」で、失敗したデータ取得がやり直され、成功すれば通常の画面に戻る
- [x] エラー表示の状態で別の画面へ移動すると、移動先の画面が通常どおり表示される
- [x] 存在しないレッスン（`/lessons/no-such-lesson`）を開くと、「レッスンが見つかりません」と表示され、メニューから移動できる
- [x] 画面単位の境界の外で例外が起きても、真っ白にならず、アプリ全体の境界の表示が出る
- [x] 既存の E2E テストがすべて通る

## 4. A-2: Vitest 5 と Browser Mode

### 4.1 変更内容

| 項目                       | 変更前                                 | 変更後                                                                                                                              |
| -------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Vitest                     | 4.1                                    | 5.1（全パッケージ）                                                                                                                 |
| フロントのテスト実行環境   | jsdom（Node 上でブラウザを模倣）       | 本物の Chromium（Playwright 経由の Vitest Browser Mode）                                                                            |
| 部品の描画                 | `@testing-library/react`               | `vitest-browser-react`                                                                                                              |
| 操作と検証                 | `userEvent` / `screen` / `expect(...)` | ロケーター（`getByRole` など）と `expect.element(...)`（自動で待つ）                                                                |
| API のモック               | MSW の Node 版（`msw/node`）           | MSW のブラウザ版（`msw/browser`）。Service Worker の配信には MSW の Vite プラグインを**テスト時だけ**使い、本番のビルドには含めない |
| API のテスト（`apps/api`） | Workers ランタイム（Vitest 4）         | Workers ランタイム（Vitest 5）。書き方は変えない                                                                                    |

### 4.2 守ること

- 未登録の API を呼んだらテストを失敗させる設定（`onUnhandledFrame: 'error'`）を維持する
- テストの件数と検証内容は減らさない。jsdom 向けに書いていた検証は、同じ意図のまま Browser Mode の書き方に置き換える
- CI（GitHub Actions）でも Chromium で実行する

### 4.3 受け入れ条件

- [x] `npm test` で、フロントのコンポーネントテストが Chromium 上で実行され、すべて通る
- [x] 本番のビルド結果（`apps/web/dist`）に MSW の Service Worker（`mockServiceWorker.js`）が含まれない
- [x] CI の設定が Chromium を用意してからテストを実行する

## 5. A-3: React Compiler

### 5.1 変更内容

- `@vitejs/plugin-react` が提供する `reactCompilerPreset` を、`@rolldown/plugin-babel` 経由で有効にする。安定版の React Compiler 1.0（Babel 版）を使い、実験的な Rust 版は使わない
- すべてのコンポーネントとフックを対象にする（`compilationMode` は既定のまま）
- ESLint に、React Compiler の前提（描画中に値を書き換えない、など）を検査するルール一式（`eslint-plugin-react-hooks` の `recommended-latest`）を加える

### 5.2 受け入れ条件

- [x] 本番のビルド結果に、React Compiler が出力するランタイム（`react/compiler-runtime`）の呼び出しが含まれる
- [x] `npm run lint` が、追加したルールを含めてエラーなく通る
- [x] すべてのテストと E2E テストが通る（最適化によって動作が変わらない）

## 6. テスト計画

| 種類                 | 追加・変更するテスト                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------ |
| コンポーネントテスト | 画面単位の境界: 描画エラーの表示、「再試行」での復帰、メニューが残ること、API のエラーメッセージの表示 |

## 8. 実装中に見つかった不具合（同時に修正）

| 項目 | 内容                                                                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 症状 | レッスンのクイズに合格した後「次のレッスン」へ進むと、次のレッスンにも「完了」の表示と前のレッスンの採点結果が残り、解答できない                    |
| 原因 | React Router は URL のパラメータが変わっても同じコンポーネントを使い回すため、クイズ送信の状態（`useSubmitQuiz`）が前のレッスンのまま残っていた     |
| 修正 | レッスン画面の中身を、レッスン ID を `key` にした別のコンポーネントに分け、レッスンごとに作り直す（`apps/web/src/features/lessons/LessonPage.tsx`） |
| 確認 | 修正前のコードで E2E テストが失敗し（「完了」が表示されたまま）、修正後に成功することを確認した                                                     |

## 10. リスクと対応

| リスク                                                  | 対応                                                                                           |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| React Compiler が想定外のコードを最適化して動作が変わる | 全テストと E2E で確認する。問題があれば、そのファイルに `"use no memo"` を書いて対象外にできる |
| Browser Mode のテストが jsdom より遅い                  | Chromium の起動で数秒増えるのみ。並列実行は Vitest に任せる                                    |
| Browser Mode には手元に Chromium が必要                 | E2E と同じく `npx playwright install chromium` で用意する。手順を `docs/testing.md` に記載する |
| 検索のたびに画面全体が読み込み中になる                  | 検索・ページ送りの一覧は `useQuery` のまま残す（3.3）                                          |
