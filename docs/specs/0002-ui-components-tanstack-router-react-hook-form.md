## 3. B-1: Tailwind CSS と UI 部品

### 3.1 方針

| 項目             | 内容                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| CSS              | Tailwind CSS v4。`apps/web/src/styles.css` の手書き CSS は廃止し、色などのデザイントークン（CSS 変数）だけを残す            |
| UI 部品          | shadcn/ui と同じ方式で `apps/web/src/components/ui/` に置く。部品のソースコードはこのリポジトリが持ち、自由に書き換えられる |
| 部品の土台       | Base UI（`@base-ui/react`）。キーボード操作と読み上げへの対応を土台に任せる。資料のとおり、shadcn/ui の新しい標準に合わせる |
| 見た目の切り替え | `class-variance-authority`（`cva`）で、ボタンの種類などの「バリエーション」を型付きで定義する                               |
| ダークモード     | 従来どおり、OS の設定（`prefers-color-scheme`）に従う                                                                       |

> **追記（仕様書 0003）**: その後、配布元への接続が許可されたため、仕様書 0003 で公式 CLI の部品に置き換えた。

**shadcn/ui の CLI について**: shadcn/ui は通常、CLI が配布元（`ui.shadcn.com`）から部品のソースを取り込みます。この開発環境からは配布元に接続できないため、同じ構成（Base UI + Tailwind + `cva` + `cn()`）で部品を書き起こします。部品がリポジトリ内のソースコードとして存在する、という shadcn/ui の性質は同じです。将来 CLI を使う場合も、同じ場所（`components/ui/`）に置かれます。

### 3.2 用意する部品

| 部品                     | 用途                                                               |
| ------------------------ | ------------------------------------------------------------------ |
| Button                   | すべてのボタンとボタン型のリンク（種類: 標準・強調・控えめ・危険） |
| Input / Textarea / Label | フォームの入力欄                                                   |
| NativeSelect             | 選択欄（ブラウザ標準の `<select>` を同じ見た目に整えたもの）       |
| Card                     | 各画面の囲み                                                       |
| Badge                    | 「完了」などの小さな表示                                           |
| Progress                 | 章ごとの進み具合                                                   |
| RadioGroup / Checkbox    | クイズの選択肢                                                     |
| AlertDialog              | 削除の確認                                                         |
| Toast（Base UI）         | 操作結果の通知（9 章の 1 を参照）                                  |

### 3.3 部品の型

- 各部品は、元の HTML 要素（または Base UI の部品）が受け取れる属性をすべて受け取る（`ComponentProps<'button'>` などとの交差型）
- バリエーションの型は `cva` の定義から `VariantProps<typeof buttonVariants>` で導出し、手書きしない

### 3.4 振る舞いの変更

| 画面                     | 変更前           | 変更後                                                                        |
| ------------------------ | ---------------- | ----------------------------------------------------------------------------- |
| ノートの削除             | `window.confirm` | 確認ダイアログ（AlertDialog）。Esc で閉じる、フォーカスがダイアログ内に留まる |
| ノートの作成・更新・削除 | 通知なし         | 画面の端に通知（「ノートを保存しました」など）                                |
| ブックマークの追加・削除 | 通知なし         | 同上                                                                          |

## 4. B-2: TanStack Router

### 4.1 方針

| 項目             | 内容                                                                                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ルートの定義     | ファイルベース。`apps/web/src/routes/` のファイル名が URL になり、型付きのルート一覧（`routeTree.gen.ts`）が自動生成される                                                    |
| ファイルの分け方 | `routes/` のファイルは「URL と、読み込み・認証の設定」だけを持つ薄い層にする。画面の中身は従来どおり `features/` に置く（資料の「featuresからルーティングの知識を外す」方針） |
| リンクの型       | `<Link to="/lessons/$lessonId" params={{ lessonId }}>` のように、存在しない URL やパラメータの書き漏れがコンパイルエラーになる                                                |
| 生成ファイル     | `routeTree.gen.ts` はリポジトリに含める（型チェックで使うため）。手で編集しない。開発サーバーとビルドが自動で更新する                                                         |

### 4.2 認証

| ルート                                        | 動作                                                                                                                         |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| ログインが必要な画面（`_authenticated` 以下） | 表示する**前に**（`beforeLoad`）ログイン状態を確かめ、未ログインなら `/login?redirect=元のURL` へ移動する                    |
| ログイン・新規登録（`_guest` 以下）           | ログイン済みなら、`redirect` の値（なければトップ）へ移動する                                                                |
| 戻り先（`redirect`）                          | 検索条件のスキーマで検証する。アプリ内のパス（`/` で始まり `//` で始まらない）以外は捨てる（オープンリダイレクト対策を維持） |

画面の部品（`RequireAuth` / `GuestOnly`）での判定は廃止します。データを守るのは従来どおり API 側の認証・認可です。

### 4.3 型付きの検索条件

ノート一覧の検索条件を Zod スキーマで定義し、ルートの `validateSearch` に渡します。

| 項目       | 型と既定値                       | 不正な値のとき |
| ---------- | -------------------------------- | -------------- |
| `page`     | 1 以上の整数。既定値 1           | 1 として扱う   |
| `q`        | 100 文字以内の文字列。既定値は空 | 空として扱う   |
| `lessonId` | レッスン ID の形式。省略可       | 省略として扱う |

画面の部品は、検証済みで型の付いた値（`page: number` など）を受け取ります。URL を手で書き換えて不正な値を入れても、画面はエラーにならず既定値で表示します。

### 4.4 データの読み込み

- 各ルートの `loader` で、画面に必須のデータの取得を**表示より先に**開始する（`queryClient.ensureQueryData`）。画面の部品は従来どおり `useSuspenseQuery` で同じデータを読む
- リンクにマウスを乗せた時点で、移動先のデータの取得を始める（`defaultPreload: 'intent'`）

### 4.5 仕様書 0001 と PR #1 の動作の引き継ぎ

| 動作                                                             | 実現方法                                                                                                                |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 画面のエラーでもメニューが残り、「再試行」で取得し直す           | ルーターの `defaultErrorComponent`。再試行で TanStack Query のエラーを解除し、ルートを読み直す（`router.invalidate()`） |
| 別の画面へ移動するとエラー表示が解除される                       | ルーターの標準の動作                                                                                                    |
| 読み込み中の表示                                                 | ルーターの `defaultPendingComponent`                                                                                    |
| どこにも受け止められなかった例外でも真っ白にならない             | `AppErrorBoundary`（変更なし）                                                                                          |
| 次のレッスンへ移動したとき、前のレッスンのクイズ結果が残らない   | ルートの `remountDeps` で、レッスン ID が変わったら画面を作り直す（`key` による回避策を置き換える）                     |
| 画面を移動したら先頭へスクロールし、戻る・進むでは位置を復元する | ルーターの `scrollRestoration`（自作の `ScrollToTop` を置き換える）                                                     |
| ノートの検索・ページ送りではスクロール位置を保つ                 | 検索条件だけを変える移動で `resetScroll: false` を指定する                                                              |
| 存在しない URL                                                   | ルーターの `defaultNotFoundComponent`                                                                                   |

### 4.6 受け入れ条件

- [x] 未ログインで保護された画面を開くと、画面を描画せずにログイン画面へ移動し、ログイン後に元の画面へ戻る

## 5. B-3: React Hook Form

### 5.1 方針

| 項目             | 内容                                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| 選定             | React Hook Form。利用者が最も多く、資料も「そのままでよい」としている。TanStack Form は新規の選択肢として記録に留める |
| 検証             | `@hookform/resolvers` の `zodResolver` に、API と同じスキーマ（`packages/shared`）を渡す                              |
| 型               | フォームの値の型はスキーマから導出する（`z.input` が入力中の型、`z.infer` が送信時の型）                              |
| サーバーのエラー | API が返す項目ごとのエラーを `setError` で各入力欄に表示し、項目に属さないエラーはフォーム全体のエラーとして表示する  |
| 対象             | ログイン、新規登録、ノートの作成・編集                                                                                |

### 5.2 振る舞い

- 送信時に検証し、エラーのある項目にフォーカスを移す
- 一度送信した後は、入力のたびに検証し直してエラー表示を更新する
- 送信中はボタンを無効にする

### 5.3 受け入れ条件

- [x] 3 つのフォームで、入力の誤りが項目ごとに表示され、API は呼ばれない
- [x] API が返した項目ごとのエラー（例: 存在しないレッスン）が、該当する入力欄に表示される
- [x] 送信後に誤りを直すと、送信し直さなくてもエラー表示が消える

## 8. 実装時の判断と仕様からの変更

| #   | 当初の仕様                                          | 実装                                                                                                        | 理由                                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 通知に sonner を使う                                | Base UI の Toast を使う                                                                                     | sonner は読み込み時に `<style>` 要素を動的に追加するため、このアプリの CSP（`style-src 'self'`）でブロックされた（E2E の「コンソールにエラーが出ない」テストで検出）。CSP にハッシュを足す方法もあるが、sonner の更新のたびに値が変わる。Base UI はすでに使っており、`<style>` を追加しない |
| 2   | 表示前の取得に `queryClient.ensureQueryData` を使う | `queryClient.query` を使う                                                                                  | 導入した TanStack Query の版で `ensureQueryData` が非推奨になっていた（lint で検出）。`query` は「新しければキャッシュ、古ければ取得し直す」で、画面側の `useSuspenseQuery` と同じ考え方になる                                                                                              |
| 3   | （記載なし）                                        | テストではリンクのマウスオーバーによる先読みを無効にする                                                    | 先読みはマウスの位置で API の呼び出しが変わるため、テスト結果が不安定になる。本番では有効                                                                                                                                                                                                   |
| 4   | （記載なし）                                        | E2E テストはテストごとに別の接続元（`CF-Connecting-IP`）として API を呼ぶ                                   | E2E の件数が増え、API のレート制限（ログイン・登録は接続元ごとに 1 分 10 回）に達した。本番では Cloudflare がこのヘッダーを実際の接続元で上書きするので、偽装には使えない                                                                                                                   |
| 5   | （記載なし）                                        | ルーターの `scrollRestoration` に置き換えたうえで、検索条件の既定値を URL に書かない（`stripSearchParams`） | `/notes?page=1&q=` ではなく `/notes` になり、URL が読みやすくなる                                                                                                                                                                                                                           |
| 6   | （記載なし）                                        | コンポーネントテストでも本番と同じ CSS を読み込む                                                           | 読み込まないと、大きさが CSS で決まる部品（Base UI のラジオボタンなど）が「見えない」と判定される。見た目の不具合も検出できるようになった                                                                                                                                                   |
| 7   | （記載なし）                                        | 通知のタイトルを見出し（`h2`）ではなく段落にする                                                            | Base UI の既定は見出しで、ページの見出し構造に通知が混ざっていた（E2E で見出しを探す処理が通知に一致して検出）                                                                                                                                                                              |

## 10. リスクと対応

| リスク                                                                                             | 対応                                                                                                    |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| ルーターの置き換えで画面遷移の挙動が変わる                                                         | 既存の E2E テストをすべて通すことを条件にする                                                           |
| 生成ファイル（`routeTree.gen.ts`）が古いまま残る                                                   | 開発サーバー・ビルド・テストの実行時に自動で更新される。CI のビルドで不整合があれば型チェックで失敗する |
| Base UI の部品の HTML 構造がブラウザ標準の要素と違う（例: ラジオボタンが `<button role="radio">`） | テストは役割（role）とラベルで要素を探しているので影響しない。キーボード操作は Base UI が担う           |
| 見た目の全面的な変更で、使い勝手が下がる                                                           | 画面の構成と文言は変えない。スクリーンショットで変更前後を比べる                                        |
