# 仕様書 0004: Cloudflare の Rate Limiting による二段構えのレート制限

| 項目   | 内容                                                                        |
| ------ | --------------------------------------------------------------------------- |
| 状態   | 実装・本番確認済み                                                          |
| 作成日 | 2026-11-15                                                                  |
| 対象   | `apps/api`（レート制限のミドルウェア、Worker の設定、テスト）、ドキュメント |

## 1. 背景と目的

これまでのレート制限は、D1 にカウンターを置く固定ウィンドウ方式だけでした（`rate_limits` テーブル）。この方式には次の弱点があります。

| 弱点                  | 内容                                                                                                      |
| --------------------- | --------------------------------------------------------------------------------------------------------- |
| 大量の攻撃に弱い      | 数えるたびに D1 へ書き込むので、大量のリクエストを受けると処理が追いつかない                              |
| D1 の無料枠を使い切る | 攻撃のリクエストでも 1 件ごとに D1 の書き込みが発生する。無料枠を使い切ると、アプリ全体の書き込みが止まる |
| 遅い                  | 判定のたびにデータベースとのやり取りが発生する                                                            |

商用のサービスでは、Cloudflare の WAF やレート制限の機能を組み合わせて使います。このアプリでも、無料で使える方法で同じ考え方を取り入れます。

## 2. 方法の比較と判断

| 方法                                    | 無料プラン                                           | `*.workers.dev` で使えるか     | 採否     |
| --------------------------------------- | ---------------------------------------------------- | ------------------------------ | -------- |
| Workers の Rate Limiting バインディング | 使える                                               | 使える                         | **採用** |
| WAF のレート制限ルール                  | 1 ルールのみ。数える期間・遮断する期間とも 10 秒だけ | 使えない（独自ドメインが必要） | 見送り   |

Rate Limiting バインディングは、WAF のレート制限ルールと同じ仕組みを Worker のコードから使うものです。数は Cloudflare の拠点（データセンター）ごとに別々に、おおよその値で数えられます。公式の説明にも「上限を少し超えて通ることがある」とあります。

将来、独自ドメインを使うときは、WAF のルールを一番外側に足すことで、Worker が動く前に止められます。

## 3. 方針: 二段構え（多層防御）

```
リクエスト
  → 第 1 段: Rate Limiting バインディング（拠点ごと・おおよそ・速い・D1 を使わない）
      大量の攻撃をここで止める
  → 第 2 段: D1 のカウンター（拠点をまたいで正確に数える）
      第 1 段を通ったリクエストだけを数える
  → 処理
```

| 項目                | 内容                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| 数える単位          | 両段とも、接続元の IP アドレス（`CF-Connecting-IP`）ごと                                                |
| 上限の関係          | 第 1 段は第 2 段の 2 倍に緩める。普通の利用者は第 2 段の正確な上限で判定され、攻撃だけが第 1 段で止まる |
| 第 1 段で止めた場合 | D1 には書き込まない。429 と `Retry-After`（数える期間の秒数）を返す                                     |
| 応答                | どちらの段で止めても、同じ 429（`RATE_LIMITED`）を返す。どの段で止めたかは外から分からないようにする    |

### 3.1 上限

| 対象               | 第 2 段（D1） | 第 1 段（バインディング） | バインディング名              |
| ------------------ | ------------- | ------------------------- | ----------------------------- |
| 登録・ログイン     | 60 秒に 10 回 | 60 秒に 20 回             | `AUTH_RATE_LIMITER`           |
| npm パッケージ検索 | 60 秒に 30 回 | 60 秒に 60 回             | `PACKAGE_SEARCH_RATE_LIMITER` |

第 1 段の上限は `apps/api/wrangler.jsonc` の `ratelimits` に書きます（数える期間は 10 秒か 60 秒しか選べない決まり）。コード側の `RATE_LIMITS` には、どのバインディングを使うかを書きます。

## 4. テスト

| 確認すること                                      | 方法                                                                            |
| ------------------------------------------------- | ------------------------------------------------------------------------------- |
| 第 1 段で止めると 429 と `Retry-After` を返す     | 必ず拒否する偽のバインディングを渡す                                            |
| 第 1 段で止めたときは D1 に書き込まない           | 同上。`rate_limits` テーブルが空のままであることを確かめる                      |
| 第 1 段には接続元ごと・対象ごとの鍵が渡される     | 呼ばれた鍵を記録する偽のバインディングを渡す                                    |
| 本物のバインディングが Worker に設定されている    | テスト環境（workerd）の本物のバインディングを呼び、受け付けられることを確かめる |
| 既存のレート制限（第 2 段）の振る舞いが変わらない | 既存のテスト                                                                    |

本物のバインディングは時計の区切り（1 分ごと）で数え直すため、「上限を超えたら止まる」ことを本物で試すと、区切りをまたいだときに結果が変わります。そのため、拒否する場面は偽のバインディングで確かめます。また、本物の数はテストの間で持ち越されるので、テスト用のクライアントにはそれぞれ別の IP アドレスを割り当てます。

## 5. 受け入れ条件

- [x] `wrangler.jsonc` に 2 つの Rate Limiting バインディングがある
- [x] 登録・ログイン・パッケージ検索で、第 1 段 → 第 2 段の順に判定される
- [x] 第 1 段で止めたときに D1 へ書き込まない
- [x] 既存のテスト（共通・API・Web）と E2E テストがすべて通る
- [x] 本番で、普通の操作が制限されずにできる
- [x] `docs/security.md` に二段構えの説明がある

| ローカルの Worker での確認                          | 同じ接続元からログインを 25 回失敗させると、401 が 10 回（第 2 段の上限まで）、429 が 15 回。D1 の数は 20 で止まり、21 回目以降は書き込まれなかった |

## 7. 検証結果（本番環境、2026-11-15）

プルリクエスト #8 で CI の成功を確認してから `main` に取り込み、Cloudflare へのデプロイ後に確認した。

| 確認項目                           | 結果                                                                                                                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 同じ接続元からログインを 25 回失敗 | 401 が 10 回、429 が 15 回。D1 の数は 21 で止まり、残りの 4 回は第 1 段で止められて D1 に書き込まれなかった（上限 20 に対して 21 回通ったのは、拠点ごとのおおよその数え方による想定内の差） |
| 仕様書 0002 と同じ 15 項目         | すべて成功（登録・ログインを含む普通の操作が制限されない）                                                                                                                                  |
| パッケージ検索                     | 結果が返った                                                                                                                                                                                |

確認用のアカウントは削除した。

補足: 確認に使った作業環境は、出口の IP アドレスがリクエストごとに変わる。1 回ずつ接続し直して送ると、25 回が 14 個の IP アドレスに分かれ、どちらの段にも引っかからなかった。1 本の接続を使い回して、同じ IP アドレスから送って確認した。

## 8. 検証手順

1. `npm run check` と `npm run test:e2e`
2. 作業ブランチからプルリクエストを作り、CI の成功を確認してから `main` に取り込む
3. Cloudflare のデプロイ完了を確認し、本番で主要な操作（登録・ログイン・検索）を確認する。確認用のデータは削除する
